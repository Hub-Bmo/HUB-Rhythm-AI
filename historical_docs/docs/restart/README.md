# 國樂打擊樂譜資料化工具：重啟交接文件

文件日期：2026-10-27  
現行程式資料版本：`2.1`  
狀態：停止繼續堆疊現行介面，保留可用底層，以下一版的兩程式架構重新開始

## 1. 這次重啟的決定

下一階段拆成兩個程式，兩者共用同一套可攜資料，但各自只負責一種工作：

1. **樂譜圖片辨識程式**
   - 匯入與保存整份樂譜照片。
   - 確認頁序。
   - 找出譜面、小節與建議段落。
   - 讓使用者明確調整「哪張圖的哪個範圍，對應 Segment 的哪些小節」。
   - 呼叫 OpenAI，保存原始辨識候選、證據框、警告與失敗原因。
   - **不直接寫入正式 Track / Take / Event。**

2. **資料確認與格狀標註程式**
   - 載入第一個程式產生的辨識套件。
   - 對照原圖接受、修正或拒絕候選。
   - 確認樂器、擊法、重音、裝飾音、滾奏／輪奏及反覆記號。
   - 只有經人工確認後，才轉成正式 Track / Take / Event。
   - 提供格狀編修、播放、反覆展開預覽與資料匯出。

兩個程式不應同時修改同一批欄位。建議的交換格式與所有權界線見 [VNEXT_TWO_APP_DESIGN.md](./VNEXT_TWO_APP_DESIGN.md)。

## 2. 為什麼不再直接修補現行介面

現行版本把以下四件事放在同一個視窗與同一份狀態裡：

- 全頁照片與小節偵測；
- Segment 規劃；
- AI 候選審核；
- 正式格狀節奏資料。

它們彼此有隱性影響。最重要的例子是：照片上的框選若「連結到目前段落」，就會改寫該 Segment 的 `source_refs`；OpenAI 會依 `source_refs` 裁圖。之後改框會把舊辨識標為過期，但先前已寫入格狀標註的事件不會自動刪除。使用者很難從畫面判斷目前看到的是臨時框、Segment 來源框、AI 證據框，還是已正式套用的資料。

因此這次重啟不是推翻所有程式碼，而是：

- 保留已驗證的資料規則與純邏輯；
- 停止擴充現行大型介面；
- 用明確的中間資料層隔開「AI 看到了什麼」與「正式資料是什麼」。

## 3. 已確認、必須保留的需求

- 來源以樂譜照片為主，可能包含五線譜、數字譜／簡譜與部分鑼鼓經。
- 可一次匯入整份多頁樂譜，使用者先確認頁序，再調整小節與 Segment。
- Segment 可以跨頁；每一段來源必須保留照片、框選範圍與小節對應。
- 不要求程式猜樂句語意；程式只提出建議，Segment 邊界由使用者確認。
- 每個樂器各自一個 Track；同一 Segment 的 Track 在後續 token 化時才合成時間序列。
- 樂器與擊法使用穩定 ID，顯示名稱與別名可以修改；不同樂譜不可產生十種互不相干的「小鑼」。
- 原始照片、辨識進度、候選、人工修正與正式資料都要能跨重啟保存。
- 重音、裝飾音、滾奏／輪奏先由 AI 提出候選，辨識不可靠時由人工補正。
- 輪奏與滾奏視為同一類，即 `is_roll`。
- 數字譜的 `0` 是休止，不建立敲擊 Event，但時間位置仍須保留。
- 播放功能是必要的檢查工具。
- 反覆只改變播放／token 的展開順序，不複製正式 Event。
- 專案正式時間基準固定為 `960 PPQ`。

現行格式的詳細欄位與不變條件見 [CURRENT_DATA_CONTRACT.md](./CURRENT_DATA_CONTRACT.md)。

## 4. 現行版本已知且尚未解決的驗收失敗

以下是重啟前的實際觀察，**不可在新對話中假設已經修好**：

1. **反覆記號流程不清楚**
   - 現行底層可表示 `repeat_start`、`repeat_end` 與 `volta`。
   - 介面裡雖有「反覆記號…」編輯器，但入口、加入順序、適用範圍與 AI 候選如何轉為正式記號都不夠明確。
   - 尚未決定跨 Segment 的反覆應放在 Segment 層還是整首曲目的層級。

2. **照片選取範圍與 Segment 的影響不透明**
   - 藍框、橘線、灰／綠虛線、臨時框選與 AI 證據框的角色不易區分。
   - 使用者不知道改框是否會改 Segment、是否會改送給 OpenAI 的圖片，以及是否會影響已套用事件。
   - 手動在跨頁 Segment 新增來源框時，現行資料可能只帶 Segment 的整體小節範圍，沒有可靠填妥每個來源框的 `segment_start_bar` / `segment_end_bar`；這不應延續到新架構。

3. **資料套用不完整**
   - 實際試用中，只有第一個 Segment 的第 1–9 小節成功進入格狀標註。
   - 進入格狀標註的只有定音鼓一種樂器。
   - 根因尚未完成定位。現行程式只會把「目前 Segment、已接受／已修正、樂器與擊法 ID 均可對應」的候選套用；其餘資料可能被略過。下一版必須顯示逐項成功／略過原因，不得靜默消失。

4. **批次辨識可能部分成功**
   - 多頁批次中可能第一頁失敗、後幾頁成功。
   - 每個範圍必須有獨立狀態、錯誤與重試；不可用單一「整批成功／失敗」遮蔽結果。

## 5. 可以保留的現行底層

以下模組的概念可沿用，但仍要用新架構測試，不代表直接照搬 UI：

- `models.py`：Segment / Track / Take / Event 基本結構與 960 PPQ。
- `instrument_library.py`：穩定的 `instrument_id` / `stroke_id`、別名與專案快照。
- `photo_assets.py`：照片複製、雜湊去重、尺寸與相對路徑。
- `score_plan.py`、`segment_plan_apply.py`：頁序、小節序列及跨頁 `source_refs` 的概念。
- `recognition_contract.py`、`openai_provider.py`：嚴格的 AI 輸入／輸出契約與正規化座標。
- `recognition.py`：候選與人工審核狀態。
- `candidate_application.py`：只有人工確認資料才可轉成正式 Event／navigation，並建立獨立 AI Take。
- `navigation.py`：反覆展開時保留紙面 Event，不複製事件。
- `storage.py`：可攜資料夾、原子儲存、備份與匯出。

## 6. 下一階段的正確開發順序

### Phase 0：凍結與樣本保存

- 現行程式標記為 legacy，不再加新操作按鈕。
- 保存至少一個能重現下列問題的專案副本：跨頁 Segment、只有定音鼓進格、第一頁辨識失敗、含反覆記號。
- API key 不得寫入專案或測試樣本。

### Phase 1：先定資料契約，不做 UI

- 確認 vNext 的辨識套件格式。
- 為跨頁 Segment、六個以上 Track、休止、重音／裝飾音／滾奏、反覆與部分失敗寫測試。
- 明確決定跨 Segment 反覆的層級。

### Phase 2：最小可用的圖片辨識程式

- 只做匯入、頁序、小節、Segment 來源表、裁切預覽、辨識、狀態與匯出辨識套件。
- 每次送出前顯示「照片、區域、Segment、本段小節、模型」摘要。
- 不提供正式格狀資料編輯。

### Phase 3：最小可用的資料確認程式

- 先做候選逐項接受／修正／拒絕。
- 顯示每個 Segment × 樂器的候選數、未對應數、已套用數與略過原因。
- 通過審核後才建立正式 AI Take。

### Phase 4：格狀標註、播放與反覆

- 格狀檢查與播放使用正式資料，不直接讀未審核 AI 候選。
- 反覆編輯器先顯示展開結果，再允許儲存。
- 最後才做資料匯出與 token 化。

每個 Phase 完成後先由使用者試用並簽收，再開始下一個 Phase。不要在單一開發回合內同時修改資料契約、辨識提示、UI 與播放。

## 8. 模型與 token 使用策略

`GPT-5.6 Sol` 是模型；`High`／`Ultra` 是推理強度，不是另一個模型。重啟後建議：

- 平常閱讀文件、實作單一 Phase、補測試：`GPT-5.6 Sol + High`。
- 文字整理或小修：可降到 `Medium`。
- 只有資料契約定稿、跨檔遷移、重大合併前的完整稽核才用 `Ultra`。
- 每個對話只載入本次 Phase 所需文件與程式碼，不重新閱讀整段舊對話。

這份交接文件值得做一次高強度稽核，但不需要後續每一步都使用 Ultra。官方模型與推理說明：

- <https://developers.openai.com/api/docs/models/gpt-5.6-sol>
- <https://developers.openai.com/api/docs/guides/reasoning>
